# 项目目录空间审计与减量方案

测量日期：2026-10-06；对象：当前 Mac 的 Medota2 工作目录。初次审计仅分析与建议；随后用户授权实施，执行结果见文末。

## 结论与口径

项目目录约 **7.67 GiB（8.23 GB）**。构建目录和 `.medota2` 合计约 91%，是主要减量对象。Git 跟踪的 403 个文件逻辑大小合计约 16.9 MiB；源码及受版本管理资料体量很小。

采用 `du -k` 的已分配空间统计，包含隐藏目录，不沿符号链接统计外部目录；另按文件 inode 去重核对。全目录常规文件逻辑大小约 7.34 GiB，约 14.6 万个文件。文件系统块分配使占用大于内容字节数。APFS 克隆、压缩及快照可能影响最终释放量，下文为目录计量估算，不承诺等量增加磁盘可用空间。运行中的日志及缓存可能继续增长。

不包含相邻三个上游仓库、用户级 pnpm store、全局浏览器缓存及 Docker 虚拟磁盘／数据库卷。目录内约 50.8 MiB 的数据库 dump 是备份，不代表正在运行的数据库大小。

## 已验证的冗余

1. **旧 standalone 包复制本地状态。** `.next/standalone` 共 1.76 GiB，其中 `.medota2` 占 1.54 GiB。13,962 个文件全部与根目录对应文件 SHA-256 一致，无缺失或内容差异，且不是相同 inode 的硬链接。其中仅 VPK pack 就复制约 902.4 MiB，另有来源工作副本和数据库 dump。该 server.js 文件时间为 2026-08-31，用于说明构建产物年代，不用于判断游戏数据版本。
2. **测试 trace 保存两份。** `shared-tests/runs` 下 18 个 ZIP 中有 9 份冗余副本，SHA-256 核对可少存约 **191.0 MiB**。原始 `test-results` 与 HTML `report/data` 中分别保存 trace；保留完整 HTML 报告时可考虑移除已核对的原始重复附件，不能任意删报告引用的附件。
3. **数据导出保存三份。** `export` 的 objects／tables 与 repository、bundle 分别有 **4,674 个文件逐一一致**；每份占约 90.1 MiB。它们承担导出、分发和本地仓库等不同阶段职责，字节重复不代表可直接删去任何角色。Git LFS 缓存另有额外对象，不能与工作区对象不加区分地清空。
4. **构建与运行证据按次累积。** 发布目录按内容键复用，但不同输入的旧产物没有自动淘汰；测试运行目录也持续保留。Playwright 当前已配置失败保留／首次重试 trace，因此优先改善保留周期和附件重复，而非进一步削弱失败诊断。
5. **两种开发编译缓存并存。** `.next/dev/cache/turbopack` 占约 202.9 MiB；当前进程明确使用 `next dev --webpack`，webpack 缓存另占约 87.7 MiB。

当前 `next.config.ts` 已排除 `.medota2` 等本机目录，`release.ts` 也会拒绝包含 `.medota2` 的正式产物；15 个 passed 发布目录均无 `app/.medota2`。因此旧包残留不能直接证明当前构建仍有相同问题。本轮未重建，未检验所有可能的本机文件是否均被排除。

## 建议实施顺序

### 第一批：可重建构建产物，预计回收约 3.8 GiB

执行前协调其他 Session，确认没有构建／测试任务，停止共享工作台；完成后使用现有 `pnpm dev` 恢复固定预览。以下为候选范围，未执行删除。

| 操作                                                         |    预计回收 | 代价与前置核对                                                     |
| ------------------------------------------------------------ | ----------: | ------------------------------------------------------------------ |
| 删除旧 `.next/standalone`                                    |    1.76 GiB | 当前工作台运行 dev，不使用该正式包；确认没有另一个 standalone 进程 |
| 发布目录保留最近两份 passed 和明确标记需保留的版本，淘汰其余 | 约 0.82 GiB | 复用旧版本时需要重建；缺 manifest 的三个目录先确认无构建占用       |
| 清理五个旧 `.next-*` 目录                                    |    0.86 GiB | 后续对应构建／测试冷启动；日常 `.next/dev` 保留                    |
| 清理 `.next/cache` 的旧生产缓存与不再使用的 Turbopack 缓存   |    0.41 GiB | 后续生产构建或切回 Turbopack 时重建                                |

四项路径互不重叠，合计约 3.85 GiB；目录可由 7.67 GiB 降至约 3.8 GiB。保留更多指定发布版本时，回收量相应减少。清理完成后检查工作台 ready、图鉴与地图可访问，并确认 data:status 的数据 problems 为空；不要把未提交文档引起的 code-modified 误判为数据损坏。

### 第二批：测试及导出证据，按用途保留

- 先消除经哈希核对的 trace 双份保存，候选收益约 191 MiB；与后续整批淘汰测试运行的收益不能重复相加。
- 建议保留最近 10 次成功结果、最近 5 次失败完整附件，以及所有未解决问题所需证据；历史成功运行保留 run.json／摘要即可。当前所有共享测试证据合计约 504 MiB，最终收益由保留清单决定。
- 保留 `.medota2/shared-tests/environment.json` 引用的 `test-runs/integration-20261005t184425z-1e96a13d` 的状态、凭据及租约。不能把 40 个旧测试目录一并清空。
- 核对已发布数据可恢复且没有待发布候选后，可清理临时 `data-sync/export` 和已交付 bundle，目录上限合计约 266 MiB。保留当前 repository、active、sources、maps 和数据锁；保留所有受支持代码版本需要的快照，不能任意清理 Git LFS 对象。
- `pnpm test:clean` 当前清理记录的测试服务栈，**保留测试证据**，不会自动回收上述数百 MiB 文件。

### 第三批：统一来源缓存，潜在再减约 1.49 GiB

当前活动快照把运行来源指向 `data-sync/sources`，地图指向 `data-sync/maps`；`previewEnvironment()` 会传入这些路径。旧 `.medota2/cache` 仍是部分独立命令和服务读取的默认来源候选，所以先核对全部入口的引用与重建能力。

建议让 Web、导入／导出和版本显示共同使用按 commit 固定的来源解析器，核验来源清单和 checksum 后，淘汰不再被引用的旧 Git 缓存及完整工作副本。同步来源目前已使用浅抓取和 sparse-checkout，不需要把“新增稀疏检出”作为未实现功能。进一步重点是避免另一套完整来源缓存长期共存，保持离线使用与精确版本恢复能力。

此项需要配置／实现及验收，不计入第一批约 3.8 GiB 的收益。相邻上游仓库不是本次分析对象，也不能因为内容相近就一并清理。

## 长期治理建议（待实施）

- 增加统一空间盘点与清理入口：默认只预览目录、大小、引用及保留理由；显式执行时持有工作区锁，保护活动快照、租约、凭据、地图和人工标记产物。当前没有这个统一命令。
- 发布目录设置数量／体积上限，例如最近两份成功版本加人工固定版本；检查复用逻辑须确认文件仍存在，避免删除后误用旧成功缓存。
- 测试结束后生成一份可移动的完整报告，附件按内容去重；保留摘要与重现信息，失败附件按数量和体积淘汰。文档若引用被归档证据，同步记录归档位置或已清理状态。
- `server.log` 增加轮转，例如每份 10 MiB、保留 3 份。当前打开模式为追加，未见轮转实现。
- 同步流程使用临时目录并在明确交付后清理；长期可将不可变对象集中到一份内容寻址存储。优先使用可验证的复制／写时复制方案，避免可写硬链接修改共享数据。
- 保留 standalone 排除与本机状态检查，再增加产物体积异常检查；开发、验证和发布保留必要隔离，但给各目录明确生命周期。

不建议为了本项目减量优先删除 node_modules、清空整个 `.medota2` 或改写 Git 历史。依赖会在继续开发时恢复，代码 Git 仅约 27 MiB，而 `.medota2` 含当前运行身份和业务数据引用。

## 验证范围

本轮执行目录分层统计、文件字节及 inode 核对、重点副本 SHA-256 比对、运行进程与活动快照／测试租约引用检查，并阅读清理／构建／数据同步代码。没有读取或输出凭据内容，没有删除文件、停止工作台、安装依赖、修改业务实现或重跑全量产品测试。新增审计文档与任务交接记录按文档范围检查。

## 已执行清理（2026-10-06）

用户随后授权按方案执行。本轮在持有检查、发布、测试数据库、数据同步及工作台锁的情况下顺序操作，先停工作台，清理后恢复固定3000预览。

- 删除旧 `.next/standalone`、五个 `.next-*` 目录、旧生产缓存及闲置Turbopack缓存。
- 发布目录保留按manifest的builtAt排序最近两份passed版本：`c95fba00…`、`00925aac…`；删除其余16个目录，将已有manifest留存在清理清单中。
- 删除9份经SHA-256再次核对的原始trace ZIP，报告中的对应副本完整保留，约191 MiB；原始附件路径的变更可在删除清单查到保留位置。保留全部失败运行及历史摘要，不再批量淘汰未核明用途的测试证据。
- 固定来源commit的旧工作副本改为Git稀疏检出，140个清单文件全部保留且哈希一致；占用从约623.5 MiB降至16.1 MiB。Git对象库和原命令配置保留，仍可离线读取完整固定版本；没有改动业务代码、来源commit或数据锁。
- 核对有一个ready-to-restore候选，保留export、bundle及全部候选目录，避免破坏待恢复用途；此项没有计入释放量。

目录占用由约 **7.67 GiB降至3.02 GiB**，减少约 **4.65 GiB（60.6%）**，按验收后du计量。实际释放口径仍受前述文件系统条件影响。清理操作前后14,327个受保护文件逐一哈希相同，覆盖当前快照仓库、来源和地图、候选身份／凭据、共享测试租约及其目录、数据库备份和本地配置。

验收：工作台ready、sample=passed、pendingSetup为空；英雄／技能／单位／地图／数据库页HTTP200。共享真实数据流程4项通过，固定fixture数值检查1项按设计跳过；涵盖搜索／清空／筛选、详情跳转、可读悬停、手机布局及单位头像。data:status核对34表46,238行，活动快照与业务摘要保持一致，problems为空；code-modified及退出2来自未提交文档。离线data:fetch确认固定快照84,475,984字节和46,238行全部可恢复。

精确计划、删除收据、发布manifest、trace保留位置、保护校验和验收结果保存在 `.medota2/maintenance/storage-20261006/`，属于本机忽略证据。统一清理命令、自动保留策略、日志轮转和来源解析器统一仍是后续改进，本轮没有修改运行时实现或进行远程操作。

## 自动策略已落地（2026-10-06）

用户追加要求后，自动发布／测试附件保留、ZIP去重与持续日志轮转已实现；本机默认开启，CI保留验收附件。规则及配置见[README](../../README.md#自动空间保留策略)与[工作台Spec](../specs/development-workbench.md#自动保留与日志容量)。`pnpm storage:clean`只预览，`--apply`执行；来源与数据副本统一等领域治理仍保留为后续独立任务。

最终完整检查通过，6个空间专项流程覆盖删除边界及日志容量／恢复条件；真实工作台恢复ready，正式产物自动保留两份。第一次自动维护实际清理约54.8 MiB旧测试附件及48.4 MiB旧发布文件内容；这是文件内容计量，与前文du目录已分配空间口径不同。新增构建会重建必要编译缓存，因此7.67→3.02 GiB是前一次人工清理的完成时测量，不作为之后开发期间的固定大小保证。
