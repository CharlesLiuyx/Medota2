01 · 始终在一个页面看最新结果

打开一个固定开发地址，并一直留在这个页面。任何 Session 保存代码后，页面自动显示最新结果。保留当前查看的对象和参数，便于连续观察。

AI 改了什么同一个页面怎样响应
页面、样式、交互保存后热更新。编译出错时显示错误；修复后自动恢复。
查询、整理规则、计算函数自动用当前选定的小样例重跑，刷新对应结果和耗时。输入参数保持可见。
耗时较长的真实计算立即显示进度，并标明当前展示的是上一次结果。新结果完成后自动替换。
数据库结构或运行配置显示“需要迁移 / 重启”的具体原因。准备完成后恢复预览，并重新计算相关样例。
建议的首轮目标：本机预热后，大多数界面改动在 1 秒内出现，小样例结果在 2 秒内更新。用“保存文件 → 新结果可见”的实际耗时验收；冷启动和大型计算单独统计。这些是目标，尚未实测。
展开看：自动反馈需要的几个小规则
  • 复用一个开发进程和一个编译缓存。第二个 Session 启动开发时，连接已有服务，并拿到同一个地址。
  • 保存后只重跑受影响的小样例。短时间连续保存合并成一次任务，避免每次按键触发计算。
  • 每次计算携带本次输入与代码标识。旧任务晚返回时，不覆盖新任务的结果；能取消的旧任务及时取消。
  • 样例和真实数据使用同一套处理逻辑。小样例负责快反馈，真实数据用于按需验证规模与结果。
  • 开发状态仅在开发模式显示。业务页面仍按正常产品需求设计。

02 · 多个 Session 共用工作台

默认共用一个工作目录、开发分支、预览服务和开发数据库。你看到的是所有当前改动的组合。临时出现不兼容时，立即显示问题，让相关 Session 尽早协调。

  • 开工前：读当前改动和其他 Session 的简短任务记录，再确定自己要改的文件与接口。
  • 同时编辑：修改不同文件可以直接并行。碰到同一文件或同一接口时，先读最新内容，再合并小块修改；涉及同一处语义的冲突，由一个 Session 完成整合。
  • 少量操作排队：提交、切换分支、安装依赖、共享数据库迁移和重置，由一个执行者依次处理。普通代码编辑和预览继续进行。
  • 检查期间还有改动：如果相关输入变了，结果标成“已过期”，合并重跑受影响的检查。不会把旧结果当成新代码的通过记录。

每个 Session 只留一张简短任务记录：目标、涉及文件、接口变化、已做检查和当前状态。先用文件完成协作；遇到长期不兼容的实验，再按需使用独立 worktree。

展开看：测试和数据库怎样共用

浏览、筛选、查看结果等日常 E2E，可直接使用共享预览和已选定的数据版本。每次运行保留独立的浏览器状态与日志目录，减少彼此干扰。

会清空数据、故意写坏数据或试验迁移的检查，使用一个按需启动、可复用的测试数据库，并把写操作排队。检查所需的样例可局部重建。无需为每个 Session 或每次小检查创建全套容器、端口和应用。

测试输入按本次读取的数据版本固定。共享代码或有关数据在过程中改变时，本次结果失效，等待改动稳定后重跑相关场景。持续编辑时可以继续预览，提交前再取得一次对应当前内容的有效结果。

共享目录中的提交可以整合多个 Session 的成果。提交者先核对并说明本次包含的范围，避免两个进程同时改 Git 暂存区。日常协作保持当前分支；需要切换分支时先协调相关 Session。

03 · 检查、合并和 CI/CD 都按需执行

本地检查、合并检查和 CI 使用同一份“改动 → 检查范围”规则。范围相同、相关内容未变且执行环境匹配，就复用结果。内容变化后，只补做失效的部分。

E2E 以少量真实使用流程为主。它既检查能否完成操作，也核对几个已知的数值和对象关系。简单页面可以直接预览验收；容易算错的规则，再加一两个能手算答案的小检查。

已有测试按用途保留和调整。默认流程取消全量覆盖率检查；新增测试围绕实际问题和关键结果，避免为每个函数都配一套测试。

展开看：最小检查集合与结果复用
使用流程核对什么何时运行
导入一小份资料，再查询能保存，能查到，关键字段和关系正确。来源适配、保存、查询或关系变化。
打开页面，筛选并查看详情主要交互可用，显示内容与选定数据一致。相关页面、组件或查询变化。
运行一项分析，再看结果小样例答案正确；改参数后结果更新。分析能力实现后，相关计算或展示变化。
本次修改涉及的失败路径错误能定位，修复后可以恢复。本次引入或修复了相应失败情况。

这些流程可以拆成短场景，按需选择。手机、视觉快照、并发压力、完整真实数据和性能测试，分别按所改内容启用。不会每次全部运行。

首版检查范围由少量目录与功能映射组成，并补上共享模块、样例、SQL 和配置的关系。记录每条规则为什么触发；发现漏选就修正规则，无需先建设通用依赖分析平台。

一条可复用结果至少记录：所查内容及其依赖的标识、测试与样例标识、相关配置和工具版本、结果和耗时。缺少这些信息时重新检查。文件删除、重命名、配置变化和依赖更新也参与判断。

类型检查采用 TypeScript 已有的项目级增量能力；格式和 lint 可按文件执行。测试筛选只使用工具确实支持的粒度，不假设所有构建都能细分到单个文件。

展开看：合并、CI 和发布的最短路径
  1. 本地整合：共享目录里的修改先即时配合起来。保存时不创建 PR，不等合并流程才预览。
  2. 形成一个小提交：由一个执行者整理本次改动。若已有有效结果覆盖该提交，直接复用；冲突解决产生的新内容补做对应检查。
  3. 触发 CI：先判定范围，再准备需要的浏览器、数据库和构建工具。相同分支的旧检查可以合并或取消；输出“通过 / 复用 / 无关跳过 / 失败 / 已过期”。
  4. 需要 PR 时：按一个完整改动批次创建，而非每个 Session 各走一套流程。已有仓库合并规则在实施时一并核对。
  5. 需要发布时：构建发生变化的发布单元，复用已经验证的产物，并进行必要的启动检查。部署时不再次构建同一产物。

CI 成功结果仅在完整输入与执行条件匹配时复用。本机与远端的操作系统、浏览器或配置不同时，对环境敏感的检查重新执行。合并后的新增组合也要纳入检查范围。

当前仓库尚无远程生产部署流程。CD 先保留一个薄发布入口，部署目标明确后接入；当前 Web 若仍是一个应用，按应用构建。未来计算组件可独立发布时，再按组件执行。

全量 pnpm verify 保留为显式诊断或大范围工具链变更的选项，不再是每次 PR 和 main 推送的默认入口。

04 · 换模型或工具时，直接接手

项目共识写在仓库里，启动和检查使用普通命令。Codex、Claude Code 和 OpenCode 读取同一组事实，调用同一组入口。模型升级时，继续使用这些文件和命令即可。

放在哪里保存什么
AGENTS.md共同工作规则：如何启动、共享协作、按需检查、保存进展。保持简短。
CONTEXT.md项目目标、核心概念、模块入口和主要边界。细节链接到对应代码或文档。
docs/current.md 拟新增当前阶段、已确认决定、待办、已知问题和下一步。阶段结束时更新。
.medota2/sessions/<id>.md 拟新增每个 Session 自己维护一份本机任务记录。其他 Session 按需读取，减少多人改同一任务板的冲突。
docs/adr/只记录影响长期选择的重要决定，例如数据迁移、接口变化或新增运行时。

每次接手先读入口、当前进展和相关 Session 的记录，再读所改模块。改完后补上接口变化、检查结果和遗留问题。结束或交接时，把仍需继续的事项写入当前进展文档。上下文按相关性展开，完成状态以当前文件为准。

展开看：三个工具怎样读取同一套规则
工具拟采用的连接方式
Codex读取 AGENTS.md。在其中明确要求开工时读取 CONTEXT.md 和 docs/current.md。
Claude Code使用很短的 CLAUDE.md，以 @AGENTS.md、@CONTEXT.md、@docs/current.md 导入同一组文件。
OpenCode读取 AGENTS.md；通过 opencode.json 的 instructions 加载其余入口文档。

读取机制已核对官方文档：Codex 的 AGENTS.md、Claude Code 的文件导入、OpenCode 的 instructions。这些机制支持共用文档；具体接入仍需在本机验证，并核对实际生效的全局和目录规则。

新工具或新模型接入时，做一次小验收：让它找到当前目标、启动共享预览、完成一个小改动并执行对应检查。长时间运行的 Session 在任务切换或接口变化后重新读取相关上下文。

上下文中记录配置项名称和用法，凭据继续保存在现有凭据配置中。任务记录保留必要事实；稳定结论收进仓库文档，避免长期依赖某个工具的私有聊天历史。

展开看：怎样保留迁移和回退空间
  • 通用流程落在仓库脚本中。客户端配置只负责指向这些脚本和文档。
  • 核心逻辑通过小而明确的输入输出连接。外部服务、AI 工具或引擎替换时，主要改连接处。
  • 原始输入与分析所用版本继续保存，派生结果可以重新生成。数据格式有版本号，变化时提供迁移或兼容读取。
  • 新增字段和接口优先采用兼容改法。需要删除数据或改变旧语义时，先准备备份恢复或新旧并存路径。
  • 代码用小提交保存可回退点。数据库回退单独设计；回退代码不等于恢复被删除的数据。

目标是让未来更强的模型容易理解、修改和替换实现。实际能力提升仍通过同一组小样例、使用流程和性能记录确认。

05 · 重计算独立运行，慢的部分可替换

网页负责交互和显示。大量解析、数值计算和批处理交给独立计算任务，避免它们占住页面响应。任务报告进度、耗时和错误，结果完成后回到同一个页面。

  • 开发用小样例：几秒内得到可比较的结果，保持即时反馈。
  • 真实任务少做重复工作：输入版本、参数和计算版本都相同时复用结果；发生变化时重算受影响部分。
  • 先找最慢的一步：记录总耗时、内存峰值和各阶段耗时。优先改算法、查询、数据复制与批量读写，再增加并行。
  • 给大任务留边界：限制并行数量，支持取消和必要的中断续算，为开发页面保留计算资源。

继续沿用现有技术栈。若测得某个热点需要更快的实现，再通过小接口替换为 Rust 等实现。比较结果正确性、耗时和内存后决定是否切换。

展开看：性能检查怎样保持轻量

保留一组小样例检查答案，再保留一组代表性输入测性能。只有计算代码、相关查询、数据格式或依赖发生变化时运行对应性能检查。基准记录输入量、耗时、峰值内存和运行环境。性能基准顺序执行，避免其他大计算干扰比较；日常开发优先给实时预览留出资源。

轻微计时波动只提示；出现可重复的明显退化，再定位并修复。优化顺序沿用现有技术选型：减少计算与复制、改 SQL 和索引、流式与批量处理、控制并行，最后评估替换语言。

任务接口先作为同仓库内的明确边界。只有需要跨进程或跨语言时，才固定传输协议及兼容版本。缓存结果与检查结果都必须随相关实现和输入变化而失效。

06 · 先落地哪几项

  1. 先打通同页实时反馈

    统一开发入口，复用一个服务。接上页面热更新、小样例自动重跑和同页错误提示。验收：两个 Session 分别改界面和计算，保存后都能在当前页面看到。

  2. 再缩短检查和整合流程

    补上按功能选择 E2E、复用环境与有效结果。让本地和 CI 共用范围规则。验收：改一个页面只触发对应场景；改文档不启动数据库和浏览器。

  3. 整理跨工具的上下文入口

    精简共同规则，接入三个客户端的文档入口和 Session 记录。验收：换一个工具或模型后，能接着完成小改动、预览和必要检查。

  4. 补齐计算边界和性能记录

    将重计算接入任务接口，并留下一组基准。验收：计算期间页面可操作；旧任务不覆盖新结果；替换计算实现时能比较正确性和速度。

实施时逐项替换当前默认流程，并同步更新对应规范。先拿到更快的反馈，再根据真实开发体验继续删减步骤。

07 · 实施时需要核对的细节

现有脚手架中，哪些地方需要改变
当前已有拟调整为
pnpm dev 启动 3000；pnpm local 启动另一套本地审阅环境。以一个固定开发入口为日常工作台，复用现有服务。真实数据按任务需要接入。
CI 在每个 PR 和 main 推送上调用完整 pnpm verify。先计算改动范围，再执行需要的任务；相同条件的有效结果复用。
verify 包含全仓格式、lint、类型、单测覆盖率、数据库、构建及 E2E。格式与 lint 按文件；类型原生增量；相关 E2E 为主；构建、数据库和性能任务按需。
每次集成 / E2E 新建数据库栈、端口、应用和产物目录。日常检查复用共享服务；破坏性检查用可复用测试库并排队。日志仍可区分每次运行。
测试命令入口只接受 suite，未转发文件或场景筛选参数。先实现确实可用的筛选入口，再接入范围选择规则。
Playwright 配置强制使用独立 Harness 与新服务。增加共享服务检查模式；按需保留独立运行能力。
当前环境规范强调每次运行独占资源及每连接身份检查。本地开发默认轻量：集中目标配置、启动时核对、明确数据用途；保留必要数据库约束和操作权限。
CONTEXT.md 目前包含较多环境机制细节。入口保留目标、概念与模块地图；详细环境规则放到按需阅读的文档。
已有 TypeScript Worker、批量导入与 Rust 演进原则。复用这些基础，补自动样例反馈、可替换计算边界和有针对性的性能记录。

这份方案会替代 ADR 0006、环境验证 Spec 中有关“日常每次运行都独占资源”和“CI 默认全量 verify”的对应要求。本地环境部分需要一份简短的替代决策，写清新默认、仍保留的约束和迁移步骤。

普通共享开发与正式数据的持久保存仍有明确用途。改用轻量流程时，先让入口、配置和文档一致，再逐步移除失去用途的旧机制。现有数据库和其他 Session 的工作持续保留。

目标命令入口与脚本范围
入口用途与现状的区别
pnpm dev启动或复用共享工作台。名称已有；自动复用、样例重跑和同页状态需要新增。
pnpm check列出范围、理由，复用或运行必要检查。新入口；承接本地、整合与 CI。
pnpm bench运行指定计算场景的基准。新入口；仅在相应性能风险出现时运行。

这几个入口编排现有 Next.js、TypeScript、Playwright、数据库脚本和 GitHub Actions。命令可从任意 AI 工具或终端调用；仓库只维护一套核心实现。

前两项优先落地。发布平台、复杂调度或新的计算语言，在有明确需要时再扩展。

这套脚手架本身怎样验收
  • 两个不同工具的 Session 同时修改不同功能，共享页面能显示组合后的结果。
  • 两个 Session 修改同一接口时，错误尽早可见，任务记录能帮助定位和协调。
  • 连续保存时，计算任务合并；旧结果不会覆盖新结果。
  • 只改文档时，CI 不准备数据库和浏览器。只改一个功能时，检查清单说明需要哪些流程。
  • 检查期间相关代码发生变化时，结果标为过期；稳定后只补做有关检查。
  • 切换 AI 工具或模型后，能从仓库找到目标、当前进展、启动和检查方式。
  • 重计算期间页面保持可操作，并且能看到进度、取消任务、比较计算结果和耗时。
