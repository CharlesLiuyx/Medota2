# 系统优化 Todo：实体版本化与版本间语义 Diff

状态：**架构与7.41e／7.41f两版真实收录已实施**。更新：2026-10-07。任务标识：`SYS-ENTITY-VERSION-DIFF`。合同见[实体版本](../specs/entity-versions.md)，决策见[ADR0009](../adr/0009-entity-release-read-context.md)。

## 目标与使用场景

先确定系统完整的实体对象范围，再为实体的版本状态关联对应版本标识，例如游戏版本号、客户端构建号等 ID。前端通过版本筛选，查询并展示该版本的实体、属性和关系；历史版本持续可读。

系统要清楚表达版本的渐进演变：两个版本之间改了哪些实体、哪些属性，增加或调整了什么关系，引入了什么新机制或逻辑，以及这些变化的来源依据。不能将这项目标缩减成“切换本工作区所选数据库的当前目录版本”。

典型使用流程：选择版本 A 查看当时的完整资料，切换到版本 B 查看对应状态，再比较 A → B 的结构化变化；需要时继续查看 B → C 或 A → C。不同页面或用户可以同时查看不同版本，页面版本筛选不应要求切换工作区的数据库。

## 当前基础与差距

立项基线为 `a735968`，以下记录当时的实现；本轮以 `main / 4fdce38` 重新核对，已落地内容见末节：

- Hero／Ability／Facet 及关系已有 `dataset_version_id`；Catalog 内容按版本保存，现行合同要求产品查询从 current head 进入。已有版本化存储可以复用，但尚未形成面向用户的统一多版本查询与比较体验。
- 已有 Catalog 差异与导入门禁；当前主要服务“候选相对当前版本是否可采用”。需核对真实差异粒度，扩展为可查询、可解释的跨版本变化模型。
- 单位定义仍从匹配 Catalog 的固定来源构建只读模型，尚无独立持久化 Unit Dataset；不能遗漏其版本状态与变化记录。
- 地图已有独立版本包及前端版本选择。图片、来源、客户端构建和 Catalog 各有自己的版本证据，不能把它们当作同一个版本号。

## 已确认的目标要求

### 1. 明确实体、属性、关系与机制的范围

- 盘点已实现及计划纳入的对象，逐项定义身份、属性、关系、来源和版本归属。至少核对英雄、技能、命石、单位、地图中的对象及区域；明确本地化、图片绑定、规则与机制分别属于实体、属性、关系还是附属资料。
- 地图中的对象实例与单位定义分别建模，明确两者关系；不要把地图位置、单位类型、来源文件与执行记录混为同一种实体。
- 为每类对象确定跨版本匹配规则，区分“同一实体发生修改”和“删除旧实体、增加新实体”。重命名、标识变化、拆分与合并须保留依据；无法确认的身份对应关系显式标为待核对。

### 2. 实体关联版本，按版本查询完整状态

- 明确实体稳定身份与该实体在某版本下的状态；以版本关联字段或关联结构表达实体、属性和关系属于哪些版本。字段及物理表设计在实施方案中确定。
- 建立可查询的版本标识及对应关系，覆盖游戏版本、客户端构建、来源快照和内部数据集版本。不能假定游戏补丁与客户端构建一一对应；未知关联保留未知，不猜测补齐。
- 未变化的实体应能在后续版本中正确查询；变化、新增和删除均有明确的版本语义，避免只返回该版本“发生变化的几条记录”。
- 列表、详情、实体间跳转、搜索、筛选和浏览器缓存都带明确版本上下文。图片、文本与地图关联须使用有依据的兼容版本，缺失时明确说明。
- 版本选择可通过 URL 恢复和分享。若保留 current head，其职责应明确为默认入口或管理选择；显式历史版本查询不能被强制覆盖为当前版本。

### 3. 将版本 Diff 建模为可解释的业务变化

Diff 以明确的 `from_version` 与 `to_version` 为边界。任意两个已收录、具有可比较内容的版本，都应能给出差异；相邻版本保留清晰的更新链，非相邻版本可查询累计后的实际差异。无变化也应有明确结果。某实体类型没有共同覆盖或版本关系未知时，返回“无法比较”及原因，不能当作无变化。

以下是需要覆盖的语义类别，名称及字段是待设计内容，例子均为示意：

| 变化类别                   | 应表达的内容                               | 示意                                      |
| -------------------------- | ------------------------------------------ | ----------------------------------------- |
| 增加／移除实体             | 身份、类型、引入或退出的版本、来源依据     | 新增一个技能定义；某单位在新版退出        |
| 修改实体                   | 身份或分类等整体变化，与属性级变化关联     | 同一实体重命名，保留身份对应依据          |
| 增加／删除／修改属性       | 字段路径、类型、旧值与新值、条件及单位     | 技能伤害从 100 变为 120；增加一个条件字段 |
| 增加／删除／修改关系       | 两端实体、关系类型、槽位／顺序／条件的变化 | 英雄新增技能关系；命石关联改为另一个技能  |
| 引入／修改／移除机制或逻辑 | 生效版本、涉及对象、条件、效果及语义说明   | 引入一种机制，或改变已有规则的计算方式    |
| 尚未解释的来源结构变化     | 原始字段或结构、来源位置、待核对原因       | 出现新结构，现有解析器尚不能解释          |

每条变化至少能追溯到版本对、对象或关系身份、变化类型、适用的字段路径与前后内容、原始来源证据，以及产生该结果的解析／Diff 实现版本。未出现、未知、空值和解析失败需要区分，防止来源缺失被误判为实体删除。

“全新逻辑”应作为可演进的规则／机制语义来表达。能够结构化的条件和效果要结构化；证据不足或尚不支持解析的部分保留原文、说明和待核对状态。来源数据变化与 Medota2 自身解析器、模型或算法升级分别记录，不能把实现升级伪装成游戏更新。

## 验收条件

1. 至少使用三个有明确来源或明确标注为合成 fixture 的版本，覆盖不变内容、属性修改、新增实体、关系变化和新机制记录；同一版本重复导入结果稳定。
2. 前端选择 A 或 B，列表、详情、关联跳转及缓存均保持对应版本；两个页面同时选择不同版本时互不影响，也不要求切换工作区数据库。
3. A → B 与 B → C 能解释渐进变化；A → C 得到实际跨版本差异，能区分中途新增又撤回、属性修改后还原等情况。无变化与不可比较有不同结果。
4. 每条 Diff 能定位到具体实体、属性、关系或规则及其来源；未知结构和身份歧义显式展示，未解析内容不被当作“没有变化”。
5. 未变实体在后续版本中仍可查到，删除、缺失和未知能区分；不混用没有版本依据的图片、文本、地图或客户端字段。
6. 旧数据迁移后历史查询仍有效；跨工作区同步后，相同版本查询与 Diff 一致。检查与验收记录注明实际代码、数据和环境基线。
